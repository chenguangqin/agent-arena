# 真实运行观察记录

模型：Bedrock `global.anthropic.claude-haiku-4-5-20251001-v1:0`，每个 profile 各运行一次。单次运行有随机性，下面的数字只用来说明现象，不作为评测结论。

## Lab2 · 重复扣款对账（2026-11-05）

| profile | 退对 | 误退 | 通知 | 输入 token | 上下文峰值 | 说明 |
|---|---|---|---|---|---|---|
| baseline | 4/8 | 0 | 4/8 | 646k | 65k | 原始 API 冗长、分页，只找到一半重复扣款 |
| tools | 8/8 | 0 | 8/8 | 25k | 7k | 组合工具一次找全；结果整形触发 20 次 |
| mcp_server（修复前） | 3/8 | 5 | 8/8 | 21k | 7k | 退了"该保留"的那一笔，见下文 |
| mcp_server（修复后） | 8/8 | 0 | 8/8 | 21k | 7k | 字段改名 + 服务端校验 |
| governance | 8/8 | 0 | 8/8 | 1306k | 90k | 原始 API + 治理；拦截 1 次，harness 代为审批 3 次 |
| governance_sdk | 3/8 | 0 | 3/8 | 295k | 44k | HumanInTheLoop 审批 3 次均正确；查找不全是原始 API 的问题 |
| full | 8/8 | 0 | 8/8 | 25k | 7k | |

可用于讲解的现象：

1. **工具设计对成本的影响最大**：同样的任务，baseline 消耗 64.6 万输入 token，`tools` 只用 2.5 万，同时正确率从 4/8 提到 8/8。
2. **任务说明的歧义 + 空结果**：第一版任务只写"11 月 3 日"，整理后的工具要求 `YYYY-MM-DD`，Agent 猜成 2024 年，查到空结果就宣布"没有重复扣款"。修复方式：任务写明年份；L2.4 对空结果追加"先核对参数"的提示。
3. **工具输出的字段顺序会误导模型**：`find_duplicate_charges` 最初先列 `keep_payment_id`、再列 `refund_payment_id`，模型对 5 笔小额订单退了要保留的那一笔。大额订单需要审批，审批服务拒绝了错误的支付单，反而退对了。修复：字段名直接写用途（`refund_payment_id`、`original_payment_do_not_refund`），并把要执行的字段放在前面；facade 的退款工具在服务端校验，拒绝退原始扣款。
4. **两层审批会相互干扰**：用 `HumanInTheLoop` 时，手写的权限 hook 先拦截了退款，HumanInTheLoop 没有机会决定。改为 SDK 模式下退款只由 HumanInTheLoop 把关。
5. **注入未被执行**：所有 profile 都没有执行订单备注中的注入指令。Haiku 4.5 在这个场景下本身能识别；L2.8 的作用更多是"出现不可信内容后强制审批"这道兜底。

## Lab5 · 大促事故处理（2026-11-05）

| profile | 规则 | 订单处理 | 通知 | 工单 | 报告 | 结束原因 | token |
|---|---|---|---|---|---|---|---|
| baseline | ✅ | 29 重放 / 11 退款 | 0/30 | 0/12 | 无 | `max_tokens` | — |
| full | ✅ | 29 重放 / 11 退款 | 30/30 | 12/12 | 三章节齐全 | `max_tokens`（恢复 3 次后） | 1.08M |

可用于讲解的现象：

1. **输出上限导致的中断**：baseline 前 4 项都做对了，之后一轮里发起太多工具调用，超出 4096 的输出上限而中断，通知、工单、报告都没做。这促成了 L5.10 输出截断恢复。
2. **扇出**：40 个订单分 5 批交给 worker，结果与环境状态一致；主 Agent 不需要逐单调用。
3. **判定器的校准问题**：判定器要求"逐条通知日志"，超出任务范围；而执行者在 finish 中报告的数量是错的（31/9/33，实际 29/11/30），判定器没有发现。主 Agent 为补证据反复生成长输出，在后半程消耗大量 token。已调整判定器提示词和门控的拉回消息，修改后尚未重跑。这个案例可直接用于 M6 讲 LLM-as-judge 的校准。
4. **devstore 曾隐藏错误信息**：MCPServer 默认屏蔽非 `ToolError` 异常的消息，模型只能看到"Error executing tool"，分不清 503 和库存售罄。已改为原样传递。

## Lab3 · checkout 间歇失败（2026-11-05）

| profile | 修复根因 | 大购物车验证 | 多改了配置 | 输入 token | 上下文峰值 | 功能事件 |
|---|---|---|---|---|---|---|
| baseline | ✅ | ✅ | `pool.max_connections` 200→300 | 16.6k | 3.1k（低估，见下） | — |
| offload | ✅ | ✅ | 无 | 133k | 17.7k | 卸载 8 次，最大一次 369,045 → 2,571 字符 |
| compaction | ✅ | ✅ | 无 | 1.30M | 161k | 压缩 2 次（11→5 条消息） |
| full | ✅ | ✅ | 无 | 11.7k（另 cache 读 43.9k） | 7.9k | 检索 7、笔记 4、即时注入 3 |

可用于讲解的现象：

1. **撞上上下文上限后的"隐性失忆"**：baseline 两次 `search_logs` 拉回约 36 万字符，连续 3 次调用报 "prompt is too long: 246639 tokens > 200000"。Strands 默认对话管理器删掉旧消息（7→4→2）后重试，Agent 丢掉了刚查到的日志，最后靠 `get_config` 直接看到可疑值才解出，并顺手改了一项无关配置。这些被拒绝的调用没有用量，trace 原先记为 0，峰值被低估；已改为按字符估算并计入峰值。
2. **压缩替代不了卸载**：单条结果就有十几万 token 时，压缩后必须保留的最近消息本身已超过阈值，compaction 总消耗 130 万 token；offload 只用 13.3 万。
3. **检索会排出过时文档**：BM25 把过时的 RB-002 排得很靠前，检索结果因此附带更新日期。
4. **SDK 的上下文预估滞后**：`projected_input_tokens` 按上一次调用推算，刚加入大工具结果时严重偏低；手写压缩改为取它和"字符数 / 3"的较大值。

## Lab4 · 连续处理 10 张工单（2026-11-05）

| | baseline | full |
|---|---|---|
| 输入 / 输出 token | 276k / 12.7k | 261k / 12.1k |
| 工具调用（前 5 张 + 后 5 张） | 57 + 54 | 48 + 49 |
| 读取 SOP 全文 | 11 次 | 0 次（加载 skill 12 次） |
| 第 3 张之后的回复附工单号（质检反馈规则） | 0/7 | 7/7 |
| T-807 按客户偏好用短信回复 | ❌ | ✅（记忆来自 T-801） |
| T-802 重复扣款退款 | ✅ | ✅ |
| T-806 / T-809 重复扣款退款 | ❌ / ❌ | ❌ / ❌ |
| 升级转人工（T-804、T-810） | ✅ | ✅ |

可用于讲解的现象：

1. **反馈记忆和偏好记忆效果最明显**：baseline 每张工单都从零开始，这两类信息完全保留不下来。
2. **Skill 省掉了读全文的步骤**，处理结果与 baseline 相同。
3. **"什么值得记"由模型决定，可能记错**：T-802 退款做对了，但没把"PG-B 重试会重复扣款"写进记忆，T-806、T-809 仍然失败；T-806 还写入了一条无用的记录（"系统只有一笔支付，已要求客户补充信息"），在 T-809 被注入。可直接用于 M4 讲记忆的写入策略和错误记忆的影响。
4. **场景修正过两处**：T-807 原先缺少配件价格（Agent 只能猜）；重复扣款原先在支付列表里直接可见，跨工单记忆没有用武之地，改为只出现在日志中。
