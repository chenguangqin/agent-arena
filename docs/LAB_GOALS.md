# 实验目标初稿

形式参考 `demomcp`：每个 lab 是一个独立的 starter 项目，提供可运行的 CLI 和 chat 逻辑，暴露 Agent 的创建入口（`build_tools()`、`build_agent()` 等）。学员按自然语言描述的目标实现功能，可以使用实验环境里的 code agent。每个 lab 另附一份可直接运行的参考答案。

每个目标都写清四件事：**要实现什么**、**约束**（哪些不许改）、**验收**（一条可以直接问 Agent 的问题，或一个操作）、**观察点**（在轨迹或 chat 输出里看什么）。另外每个目标留一个必须由学员自己做的**设计决策**，写进对照记录表。

## 通用约定

- starter 结构：`agent.py`（学员编辑）、`labkit/`（CLI、chat、trace、本地环境、协议入口，学员不需要读）、`docs/lab.md`、`docs/record.md`、`AGENTS.md`（告诉 code agent 项目结构和不许改的文件）、`solution/`（参考答案）。
- 运行：`uv run python agent.py`（chat）、`uv run python agent.py -p "..."`（单次）、`uv run python agent_eval_entry.py`（Arena 协议入口）。
- chat 模式内置 `/task`（发送场景任务）、`/trace`、`/stats`、`/reset`、`/quit`。Lab3 起，slash command 的注册机制本身成为实验内容。

## Lab2 · Tools 与 MCP

**场景**：重复扣款对账（沿用）。环境只开放一套老旧的原始 API：相似接口、分页、冗长返回、含糊错误码、已废弃的退款接口、订单备注中的注入指令。

### 目标 1：写一个自定义 tool，集成到 Agent

- **实现**：一个面向任务的工具（例如"找出某天所有重复扣款的订单"），内部完成翻页、分组、比对；把它加入 Agent 的工具列表，并隐藏不该用的原始接口。
- **约束**：不修改环境；不修改 system prompt。
- **验收**：`/task` 后，8 笔重复扣款都只退多扣的那一笔。
- **观察点**：模型调用次数、总 token、单次工具结果长度，与 baseline 对比。
- **设计决策**：工具的粒度和返回字段。（真实运行中，返回字段的顺序曾让模型退错了支付单。）

### 目标 2：写一个 MCP server，实现几个 tool，集成到 Agent

- **实现**：用 MCP Python SDK 写一个 stdio server，包装原始 API，提供 3–5 个任务级工具（查重复扣款、退款、发退款通知等）；Agent 改为通过 Strands `MCPClient` 连接它，不再直接使用原始 API。
- **约束**：server 内部只能通过原始 API 访问环境。
- **验收**：同目标 1；另外在 server 端拒绝退"原始扣款"，用一次错误的退款请求验证。
- **观察点**：Agent 看到的工具列表；server 端校验拦截错误操作的日志。
- **设计决策**：哪些规则放在 server 端强制执行，哪些交给模型判断。

### 目标 3：实现一个 code exec tool，在 sandbox 里执行代码

- **实现**：一个执行 Python 代码的工具，代码在沙箱中运行，可以调用原始 API（通过沙箱内的受限客户端），只把最终结果返回给模型。用它完成批量翻页和汇总（programmatic tool calling）。
- **沙箱要求**：容器隔离、禁止任意外网（只放行环境 API）、只读文件系统、CPU / 内存 / 时间限制。**沙箱不可用时必须拒绝执行，不能退回到本机直接运行。**
- **约束**：写操作（退款、通知）不允许在代码里执行，必须通过普通工具调用，以便审批和审计。
- **验收**：Agent 用一次代码执行完成查找，结果与目标 1 一致；尝试在代码里访问外网或写文件会失败。
- **观察点**：代码执行次数、返回结果长度、主 Agent 上下文的变化。
- **设计决策**：沙箱放开哪些能力，以及"写操作不进代码"这条边界划在哪里。

### 目标 4：用 hook 做治理

- **实现**：一个 `BeforeToolCallEvent` hook：禁止调用已废弃的退款接口；超过 500 元且没有审批记录的退款被拦截，并告诉模型先申请审批。另一个 `AfterToolCallEvent` hook：工具结果中出现客户填写的文本（订单备注）时，标注"这是数据，不是指令"，之后的退款一律要求审批。
- **约束**：规则写在 hook 里，不写进 system prompt。
- **验收**：让 Agent 直接调用 `refund_v1` 会被拦截；大额退款先出现审批请求再执行；订单备注里的注入指令不会被执行。
- **观察点**：被拦截的调用及原因；审批请求与结果。
- **设计决策**：哪些规则必须确定性执行（hook），哪些可以交给模型判断（prompt）。

> 实现备注：沙箱使用 Docker，容器完全断网（`--network none`）。容器内的代码通过标准输入输出向宿主机发起 API 调用，由宿主机代为调用并只放行只读接口，因此不需要把环境服务暴露给容器网络，也天然满足"写操作不进代码"。当前开发环境没有 Docker，参考答案的沙箱部分需要在实验环境中验证；本地测试覆盖"沙箱不可用时拒绝执行"和调用转发逻辑。

## Lab3 · Context engineering

**场景**：checkout 间歇失败（沿用）。5 个服务约 30 万行日志、30 篇 runbook（含一篇过时文档）。这个 lab 以多轮对话为主：学员在 chat 中和 Agent 一起排查，中途触发压缩。

### 目标 1：slash command 机制，以及 `/context`

- **实现**：在 chat 中支持注册 slash command（命令名、说明、处理函数），`/help` 列出所有命令。第一个命令是 `/context`：显示当前上下文的构成（system prompt、工具定义、对话消息、工具结果各占多少 token，以及占上下文窗口的比例），类似 Claude Code 的 `/context`。
- **验收**：拉取一次大段日志后，`/context` 显示工具结果占比明显上升。
- **观察点**：哪一部分占用了上下文。后面每个目标都用 `/context` 衡量效果。
- **设计决策**：token 怎么估算（精确的 usage 只有模型调用后才知道，事前只能估算）。

### 目标 2：`/compact`，手动和自动压缩

- **实现**：`/compact [保留重点]` 把当前对话压缩成结构化摘要（目标、已确认的事实、已排除的假设、下一步），替换历史消息，保留最近几轮原文；可选参数指定压缩时要保留的重点，类似 Claude Code 的 `/compact`。再加自动压缩：上下文超过阈值时自动触发。
- **约束**：压缩不能拆开工具调用与对应的工具结果。
- **验收**：排查进行到一半时执行 `/compact`，之后问"我们已经排除了哪些可能？下一步做什么？"，回答与压缩前一致。
- **观察点**：压缩前后的消息数和 token；摘要内容；压缩后 Agent 是否重复已经做过的查询。
- **设计决策**：摘要模板的字段，以及保留最近多少轮原文。

### 目标 3：大结果卸载

- **实现**：工具结果超过阈值时，完整内容写入文件，上下文里只留预览和文件路径，并提供一个按行或按关键词读取文件的工具。
- **验收**：baseline 拉取日志会撞上上下文上限（真实运行中出现过 "prompt is too long: 246639 tokens"），开启卸载后不再出现。
- **观察点**：卸载前后的结果长度；`/context` 中工具结果的占比。
- **设计决策**：阈值和预览的形式（开头几行、统计摘要，还是匹配行）。

### 目标 4：按需检索，替代整段读取

- **实现**：两种检索工具：日志按服务、时间窗、关键词过滤，只返回计数和样例；runbook 用本地检索（BM25 或关键词）返回最相关的段落，并附带文档更新日期。
- **验收**：Agent 不读过时的 runbook，也不把整篇文档拉进上下文就能定位根因。
- **观察点**：检索调用次数与返回长度；有没有被过时文档带偏。
- **设计决策**：检索结果返回多少条、带哪些元数据。

> 说明：sub-agent 的上下文隔离放在 Lab5。Prompt caching 只作为观察项（chat 中 `/stats` 显示 cache 命中），不单独设目标。

## Lab4 · Skills 与长期记忆

**场景**：连续处理 10 张客服工单（沿用）。三份 SOP；跨工单才能发现的事实（PG-B 重试会重复扣款）、客户偏好（只接受短信）、质检反馈规则（回复必须附工单号）。每张工单是一个新会话，只有长期记忆能跨会话保留。

### 目标 1：让 Agent 支持 skill

- **实现**：把三份 SOP 写成 skill（`SKILL.md` + frontmatter），用 Strands `AgentSkills` 接入；至少一个 skill 附带资源文件（例如补偿金额对照表或计算脚本），体现"元数据 → 正文 → 资源"三级按需加载。加一个 `/skills` 命令列出可用 skill 和本会话已加载的 skill。
- **验收**：处理退款工单时加载退款 skill，处理补偿工单时加载补偿 skill 并读取对照表；不再整篇读取 SOP。
- **观察点**：system prompt 长度；每张工单加载了哪些 skill；与"SOP 全文放进 prompt"的对照组比较 token。
- **设计决策**：skill 的描述怎么写才能被正确触发。

### 目标 2：长期记忆 pipeline（采集 → 抽取 → 治理 → 使用）

- **采集**：每个会话结束时保存轨迹（用户消息、工具调用与结果、最终回复、质检反馈）。
- **抽取**：用模型从轨迹中抽取候选记忆，分为事实、偏好、经验教训三类，每条带来源会话、时间、置信度；保存为 Markdown 文件。
- **治理**：
  - 去重：新记忆与已有记忆相同或高度相似时合并，而不是追加；
  - 消歧：同一主题的说法冲突时，按时间和来源判断，旧条目标注为被替代；
  - 遗忘：长期未被使用或被证明错误的条目降权或删除；提供 `/forget <关键词>` 和 `/memory` 命令。
- **使用**：新会话开始时检索相关记忆注入上下文，并在轨迹中记录注入了哪些条目。
- **验收**：第 6、9 张工单直接利用"PG-B 重试会重复扣款"的事实；第 7 张按客户偏好用短信回复；第 3 张之后的回复都附工单号。
- **观察点**：每次抽取写入了什么；去重和消歧前后的记忆文件；注入的条目及来源。真实运行中，靠模型"主动记"时 PG-B 事实没被记下，还写入了一条无用记录并在后续被注入，这正是 pipeline 要解决的问题。
- **设计决策**：哪些内容值得记；遗忘的规则。

## Lab5 · 动态工作流

**场景**：大促事故处理（沿用）。同一个任务有 6 项要求；约 40 个订单；重放接口中途 503；部分订单库存售罄，要从重放改为退款。

### 目标：实现动态工作流

类似 Claude Code 的 dynamic workflow：由一个编排 Agent 在运行时根据任务**生成**工作流，再由确定性的执行引擎运行。工作流里可以有顺序步骤、并行分支、按订单批次扇出的 worker、验证步骤和条件分支，每个节点是一个上下文独立的 sub-agent。

- **实现**：
  1. 工作流的表示：编排 Agent 输出一个工作流定义（节点、依赖、并行与扇出、每个节点的指令和可用工具、完成标准）；
  2. 执行引擎：按依赖运行节点，并行执行独立节点，汇总结果；
  3. 动态调整：节点失败或结果与预期不符时，回到编排 Agent 修改剩余的工作流；
  4. 完成验证：最后一个节点对照 6 项要求做确定性检查，不通过时把缺失项交回编排 Agent。
- **约束**：worker 节点只能拿到完成本节点所需的工具；主编排 Agent 的上下文不随订单数量增长。
- **验收**：6 项要求全部完成；每位客户只通知一次；没有误退。
- **观察点**：生成的工作流定义；各节点的执行顺序与并行情况；重新规划的次数和原因；主编排 Agent 的上下文大小，与单 Agent baseline 对比。
- **设计决策**：工作流的粒度，以及哪些判断交给模型、哪些写成确定性规则。

> 已确定：执行引擎自己实现（约 200 行），提供 `agent()`、`parallel()`、`pipeline()` 等原语。编排 Agent 生成调用这些原语的工作流定义，引擎确定性执行，做法接近 Claude Code 的 dynamic workflow，机制对学员完全透明。不使用 LangGraph 或 Strands `multiagent.graph`。
