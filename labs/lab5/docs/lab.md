# Lab5 · 动态工作流

## 场景

大促期间一条折扣规则配置错误，约 40 笔订单 checkout 失败，但已经扣了款。任务包含 6 项要求：

1. 找到出错的折扣规则；
2. 修复配置；
3. 找出受影响的订单，逐一重放下单；
4. 重放失败的订单（库存售罄）改为全额退款，同一订单不能既重放成功又退款；
5. 通知每一位受影响的客户，每位只通知一次；
6. 关闭相关工单，保存一份包含「时间线」「影响范围」「处理结果」的复盘报告。

环境的动态因素：重放接口中途会返回 503；部分订单库存已售罄；失败订单分页返回；有的客户有两笔失败订单。

## 开始之前

```bash
uv sync
uv run python agent.py --task
```

结束时打印 `stats`（总 token、上下文峰值、按 Agent 划分的 `by_agent`）和 `state`（规则是否修复、订单状态、通知了几位客户、工单、报告章节）。把 baseline 的结果记进 `docs/record.md`。单 Agent 常见的失败：完成前几项就结束；一次发起太多工具调用，超出输出上限而中断。

## 总体要求

实现一个类似 Claude Code dynamic workflow 的运行器：**编排 Agent 在运行时根据任务生成工作流，确定性的执行引擎运行它**。

- 工作流里可以有顺序步骤、并行分支、按批扇出的步骤；
- 每个步骤由一个**上下文独立**、只拿到所需工具的子 Agent 执行；
- 编排 Agent 自己不操作环境，它的上下文**不随订单数量增长**；
- 工作流定义必须是**声明式数据**，不执行模型生成的代码。

`workflow.py` 给出了一个建议的骨架，可以完全改写。`agent.py` 中 `--mode workflow` 会使用你的 `WorkflowRunner`。

---

## 目标 1：工作流的表示

**要实现**：定义编排 Agent 输出的工作流结构（节点、依赖、扇出、每个节点的指令和工具），并在执行前做静态校验：id 重复、依赖不存在、循环依赖、未知工具、扇出配置错误。

**验收**：故意让编排 Agent 输出一个有问题的工作流（或在测试中构造一个），校验能指出问题，编排 Agent 修正后重新给出。

**设计决策**：节点之间怎么传递数据——把完整数据塞进下一个节点的提示词，还是按引用（"遍历步骤 X 的输出"）？数据由谁产出——让子 Agent 把查询结果抄写成 JSON，还是由引擎直接调用查询工具？（参考答案的第一版让子 Agent 抄写 40 个订单，模型只输出了 2 个。）

## 目标 2：执行引擎

**要实现**：按依赖运行节点；依赖都满足的节点并行执行；扇出节点把列表分批，每批一个子 Agent 并行处理，再汇总结果。

**约束**：每个节点的子 Agent 只拿到该节点需要的工具；节点之间不共享对话上下文。

**验收**：`--mode workflow --task` 中能看到并行的节点和扇出的批次；`/stats` 的 `by_agent` 中，编排 Agent 的上下文峰值远小于 baseline。

**观察**：每个节点的执行顺序、批次数量；子 Agent 的 token 与上下文峰值。

**设计决策**：批次大小、最大并行度；节点输出超出上限时怎么办。

## 目标 3：动态调整

**要实现**：节点失败（例如持续 503、输出不是预期格式）时，停止启动新节点，把失败原因和已完成节点的结果摘要交回编排 Agent，让它只为剩余工作生成新的工作流；已完成的节点可以被新工作流引用，不重复执行。

**验收**：在 trace 中看到至少一次重新规划，并且重新规划后没有重复执行已完成的工作。

**设计决策**：哪些情况在节点内部处理（重试、改走退款），哪些情况上报编排 Agent。

## 目标 4：完成检查

**要实现**：工作流跑完后，对照 6 项要求做**确定性检查**（用 `env.call` 查询环境：规则、订单状态、工单、报告章节）。不通过时，把缺失项交回编排 Agent 生成补救工作流。

**提示**：商店 API 读不到"已通知了谁"。可以在节点 Agent 上挂一个 hook 记录 `notify_customer` 调用，同时用它拦截对同一客户的第二次通知。

**提示**：完成检查只能在事后发现问题，有些错误发生了就无法撤回。参考答案的一次运行中，编排者漏掉了"先修复规则再重放"的依赖，所有重放都失败，worker 随即把 40 个订单全部退款，完成检查却通过了。对不可逆的操作（退款），用 hook 设置确定性的前置条件，例如"只有重放因库存售罄失败的订单才能退款"。

**验收**：6 项要求全部完成；每位客户只通知一次；没有误退（`state` 中 `refunded_although_replayable` 为 0）。

**设计决策**：哪些要求能用确定性检查验证，哪些只能靠模型判断。
